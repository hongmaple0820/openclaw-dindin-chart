## 一、隐私问题

### 当前风险

| 方面 | 状态 | 风险 |
|------|------|------|
| 传输加密 | ❌ 无 | 消息明文传输 |
| 存储加密 | ❌ 无 | 数据库明文存储 |
| E2EE | ❌ 无 | 服务端可查看所有消息 |

### 解决方案

#### 1. 传输层加密 (TLS)
```
chat-hub ←── HTTPS ──→ 客户端
         ←── WSS ───→ WebSocket
```

#### 2. 端到端加密 (E2EE)

**方案 A**: 使用 Matrix 的 Olm/Megolm 协议
- 成熟的 E2EE 实现
- 开源、审计过

**方案 B**: 自己实现简化版 E2EE
```javascript
// 使用 X25519 密钥交换 + AES-GCM 加密
const encrypted = await encrypt(message, recipientPublicKey);
const decrypted = await decrypt(encrypted, myPrivateKey);
```

## 二、多实例中转

### 当前设计

```
┌─────────────┐     ┌─────────────┐
│  chat-hub A │────→│ RelayService│
└─────────────┘     │  (端口8274) │
                    └─────────────┘
┌─────────────┐           ↑
│  chat-hub B │───────────┘
└─────────────┘
```

**问题**：
- 每个 chat-hub 有独立的 RelayService
- 没有中央协调

### 解决方案

#### 方案 A: 中心化中转服务
```
    ┌─────────────────┐
    │  Relay Cloud    │ ← 云端中转服务
    │  (独立部署)      │
    └─────────────────┘
           ↑↓
    ┌──────┴──────┐
    ↓             ↓
chat-hub A   chat-hub B
```

**优点**：
- 统一管理
- 便于监控
- 易于扩展

**缺点**：
- 单点故障
- 隐私风险（云端可见数据）

#### 方案 B: P2P 模式
```
chat-hub A ←──直接通信──→ chat-hub B
```

**优点**：
- 无中心节点
- 数据不经过第三方

**缺点**：
- NAT 穿透复杂
- 需要发现机制

#### 方案 C: 混合模式（推荐）
```
┌─────────────┐
│ Relay Cloud │ ← 只做协调，不存储消息
└─────────────┘
      ↓ 信号
chat-hub A ←──E2EE──→ chat-hub B
```

**优点**：
- 中转服务只做协调
- 消息端到端加密
- 兼顾可用性和隐私

```
┌─────────────────────────────────────────┐
│           Relay Cloud (云端)             │
├─────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────────┐   │
│  │ Skills 市场 │  │ 共享同步服务     │   │
│  │ - 发布技能  │  │ - 用户可选同步   │   │

    ┌──────┴──────┐
    ↓             ↓
chat-hub A   chat-hub B
```

**用户选择**：
- 🔒 **隐私模式**: 数据不离开本地
- ☁️ **云同步模式**: 加密后同步到云端
- 🌐 **共享模式**: 选择性地共享 Skills 到市场
